# §A 共用色板

## A.1 设计立场：色板要**克制**，因为 L2 要能救场

`world-tour-reward §2.1 L2` 把话说死了：8 张图来自 Seedream，色温**必然不齐**，靠一层 `globalAlpha ≈ 0.12` 的区域签名色叠层把它们拉回同一调性，「比要求美术反复返工便宜得多」。

这条产线判断成立**有前提**：

> **L2 是一层薄薄的 source-over 染色，它能纠偏，但纠不了「打架」。**
> α=0.12 的染色对「色温差 200K」有效，对「一帧饱和荧光绿、一帧灰调莫兰迪」无效——后者叠完只会变成两张脏图。

所以色板纪律不是审美偏好，是**让 L2 这条省钱路径能真的省下钱**的工程前提。三条硬约束：

1. **每帧 ≤ 3 主色 + 1 点缀色**（第 8 帧严格 ≤ 3 色，无点缀色）。色少 → 色温偏差的落点少 → L2 一层就能收。
2. **全部主色为中低饱和**（HSL 饱和度 ≤ 55%）。高饱和色在 α=0.12 染色下几乎不动，会顶穿统一调性。
3. **禁纯白 `#FFFFFF` / 纯黑 `#000000` / 荧光色**。纯白不吃染色（叠完还是白），纯黑吃不动（叠完还是黑）——两端都是 L2 的盲区。用「暖米白」与「近黑深色」替代。

## A.3 三区域签名色（L2 调色叠层用）

**取值原则：零新增色。** 直接取 `game-feel-direction §2.2 光影三度表`的**暗部档**——它本身就是三个区域身份色（`REGION_COLORS`）向墨色偏移的既有推导值，已在项目色彩系统里。

| 区域 | 身份色（`theme.ts REGION_COLORS`） | **L2 签名色（暗部档）** | 建议 α | HSL 校验 |
|---|---|---|---|---|
| `amer` 美洲 | `#E0B15E` 金 | **`#B8904A`** 暗金 | **≈ 0.12** | H 36° / S 43% / L 51% |
| `euro` 欧洲 | `#5B8FB0` 蓝 | **`#47738F`** 暗蓝 | **≈ 0.12** | H 202° / S 34% / L 42% |
| `asia_afr` 亚非 | `#87A878` 绿 | **`#6B8A5F`** 暗绿 | **≈ 0.12** | H 92° / S 19% / L 46% |

**为什么用暗部档而不是身份色本体**：`#E0B15E`（L 68%）这类亮色以 source-over 叠上去会**抬黑场**——把暗部整体提亮、压掉画面的暗色氛围，随后 L3 还得再压回来，一进一出画面就发灰发脏。暗部档 L 值集中在 42–51%，叠 0.12 只染色不提亮，是唯一不打架的档位。

**三色可叠加性校验**：明度 42–51%（差 9 个点）、饱和度 19–43%，是一组明度齐平的低饱和三角色（暖金 / 冷蓝 / 灰绿）。任意两帧相邻切换时，L2 的色相跳变幅度可控，不会出现「换区域像换了台电视」。

## B.0 通用件（8 帧共用，prompt 已内联，此处单列供脚本化）

### B.0.1 风格串 `STYLE_BASE_WT`

与母题 PNG 的既有风格串同族（`flat geometric, minimal, clean vector-like, single flat color with one accent stroke, game asset`），中文化并加两个本批专属词（`旅行手账明信片质感`）：

```
扁平平涂，几何化造型，矢量感干净边缘，大色块，单色平涂不做写实渐变，柔和环境光，
旅行手账明信片质感，游戏美术资产，竖构图 9:16
```

**总纲一句话**：这套图是「周爷爷留下的明信片」——**手账 / 平涂 / 几何 / 水彩**，与游戏「风格化几何母题」美术同脉。判定标准同 `scene-backgrounds-spec §1.1`：把成图缩到 200px 宽，与任一 `cur_*.png` 并排，**边缘硬度、色彩饱和度、投影柔度三项必须读作同一套笔法**。

中文在前（主 prompt 为中文，同语种压制最有效），英文在后（沿用 pipeline 已验证有效的 token，做冗余加权）：

```
写实照片，摄影，超写实，真实光影，3D 渲染，景深虚化，镜头光晕，光斑，
真实钞票，硬币，钱币，货币符号，金钱元素，
国旗，国徽，政治建筑，军事元素，武器，
人物，人脸，人物特写，五官，人群，人手，
文字，字母，数字，标题，落款，印章，签名，水印，logo，边框，
杂乱细节，密集纹理，噪点，高饱和荧光色，纯白，纯黑，
photorealistic, photograph, realistic, hyperrealistic, 3d render, depth of field, lens flare,

```

> `写实 / photorealistic / photograph` 三处重复属**有意冗余加权**，非笔误——本批最大的翻车方向就是「Seedream 把名胜出成照片」，对写实倾向做三重压制。

### B.0.3 构图安全区（本批与 bg_* 的关键差异）

bg_* 是「按高缩放 + 居中横裁 18%」，本批**不裁切**（直出比例 = 落盘比例），但运行时会被两件事吃掉边缘：

| 吃掉边缘的来源 | 幅度 | 说明 |
|---|---|---|
| 运行时 cover-fit 到窄屏 | 左右各 **≈ 9%** | 源 9:16（0.5625）铺到 390×844（0.462）屏，横向溢出 17.8% |
| Ken Burns 推镜 `scale 1.00 → 1.06` + 平移 | 单边再 **≈ 5.7%** | 平移方向按 `帧序 % 4` 轮换，四个方向都可能 |

**合并结论（写进 prompt 与 QA）**：

- **左右各 15% 为可牺牲区** → 构图重心须落在**中央 70% 宽**
- **上下各 7% 为可牺牲区** → 构图重心须落在**中央 86% 高**
- **画面下方 40%** 是字幕区（L3② 会压暗至 `rgba(0,0,0,0.55)`）→ 必须是**低频、低对比度的延展区**（海面 / 草原 / 水道 / 雪原 / 前景山体），**不放构图重心、不放高光斑、不放高频细节**

> **⚠ 与 `world-tour-reward §2.1` 的口径澄清**：该文说 L3② 是「字幕可读性的**唯一保障**——不能依赖图本身够暗」。这条**成立且本文不推翻**。本节的底部要求是**配合**，不是替代，用来兜 L3② 管不了的两件事：
> ① **纯白大面积**：sRGB 255 的底经 0.55 黑压后为 115，与字幕色 `#FBF7EE` 对比度 **4.45:1**，卡在 WCAG AA（4.5:1）**下方一线**——L3② 数学上刚好不够；
> ② **高频细节**：浪花、砖纹、密集点阵——对比度合格也读不动，这是 L3② 完全管不到的维度。
> 详细亮度门见 §E 门 2-④。

## B.1 · 帧 1 — 日本·富士山（JPY / `asia_afr`）

**风格锚定句**（自 `world-tour-reward §4.3` 摘录并强化）
> **三层剪影**：前景北斋式几何浪纹、中景樱枝点笔、远景山体单色平涂留白顶。**3 色 + 1 点缀色，浮世绘平涂而非渐变。**

**中文主 prompt（可直接喂）**
```
浮世绘风格化平涂插画，三层剪影构图。前景是几何化的北斋式浪纹，浪头化为规整的弧形与卷曲纯色块，

天空为一整块平涂色，可有一道极简的水平云带。
整幅只用三个主色加一个点缀色：雾青（山体与远景）、暖米白（雪顶留白与天空）、深墨青（前景浪纹），
点缀色为柔粉（樱花）。构图重心落在画面中上部，画面下方五分之二为浪纹的低对比度暗色延展区，
安静、无高光斑、无高频细节。
扁平平涂，几何化造型，矢量感干净边缘，大色块，单色平涂不做写实渐变，柔和环境光，
旅行手账明信片质感，游戏美术资产，竖构图 9:16。
```

```
，无写实海浪，无浪花泡沫，无真实富士山照片，无船只，无神社，无鸟居，无灯笼，
无日文字符，无假名，无汉字，无红色落款印章，无浮世绘题跋，无人物
```

## B.7 · 帧 7 — 智利·复活节岛摩艾（CLP / `amer`）⚠ **朝向为史实硬约束**

### B.7.1 朝向纠错（本帧的第一优先级，高于一切美学考量）

`world-tour-reward §6 第 9 条`：**「第 7 帧摩艾朝向已按文档 A 的 F-2 纠正（背对海，仅阿胡阿基维 7 尊面海），美术须严格遵循。」**

字幕：**「石头几乎都背着海，只有七尊，望着远方。」**

**翻译成画面语言（不可有第二种解读）：**

| 要素 | 必须 | 禁止 |
|---|---|---|
| 石像队列朝向 | **正面朝向画面外（内陆方向）**，海平线在它们**身后**作为背景带 | ❌ 石像面朝海（背对观者、只见背影） |

| 海 | 一道清晰水平线 + 单色平涂，位于石像**之后** | ❌ 海在石像之前（会把朝向讲反） |

# §C 资产规格

## C.1 尺寸决策：选 **1080 × 1920**（不选 750×1334）

Seedream `9:16` 直出 **1440×2560**（`volcano_ark.py SIZE_MAP`），比例 0.5625，与 1080×1920 **完全一致** → 等比 Lanczos 缩放，**零裁切**（对比 `bg_*` 需横裁 18%，本批不需要，因为本批不追求匹配窄屏比例，而是交给运行时 cover-fit）。

| 候选 | 结论 | 理由 |
|---|---|---|
| **1080 × 1920** | ✅ **采用** | 见下三条 |
| 750 × 1334 | ❌ 否决 | ① 推镜 `scale→1.06` 再吃 6% 采样余量；② DPR 3 机型（1170×2532 设备像素）cover-fit 后 750 宽要放大约 1.6×，边缘明显糊——而这批图是**全屏主视觉**，不像 `bg_*` 是退让背景（糊了看不出来）；③ 走 CDN 不占主包，没有压到 750 的体积理由 |
| 1440 × 2560 直落 | ❌ 否决 | 单帧 PNG 到 1.5–3 MB，8 帧 12–24 MB。弱网首帧等待过长，而 `world-tour-reward §3.3 坑 3` 明令**「绝不能出现转圈等待——那会把『礼物』变成『加载』」**。1080×1920 量化后单帧 ≈ 250–450 KB，8 帧 ≈ 2–3.5 MB，是「能边播边补」的量级 |

> **口径澄清**：任务书写的「1080×1920 @x2」中，**1080×1920 本身即最终落盘像素**，不再乘 2。它等于逻辑视口 540×960 的 @2x，也等于 750×1334 基准的 1.44 倍——对 `world-tour-reward §2.2` 的 750×1334 布局草图有 44% 的采样余量，足够覆盖推镜与窄屏裁切。

## C.2 规格总表

| 项 | 值 |
|---|---|
| Seedream 直出 | `9:16` → **1440 × 2560** |
| 后处理 | 等比 Lanczos 缩放 → **1080 × 1920**，**不裁切** |
| 落盘格式 | **PNG**（不透明 RGB，无 alpha——全屏底图，透明通道纯属浪费） |
| 颜色空间 | sRGB |
| 量化 | `pngquant --quality 70-90`（256 色） |
| 体积门槛 | **单帧 ≤ 450 KB**，8 帧合计 **≤ 3.2 MB** |

> **色板克制的额外红利**：本批「每帧 ≤ 3 主色 + 1 点缀」的纪律，使 PNG-8 / 256 色量化**几乎无损**——平涂大色块正是 PNG 索引色最擅长的内容类型。相比之下 `bg_*` 用 `--quality 65-85` 是因为它们有柔和过渡；本批可以放宽到 70-90 且体积更小。**§A 的色板纪律不只服务视觉统一，它同时把 8 帧的下载体积砍掉了一个量级。**

### ⚠ C.4.1 两个必须交给 engineering-lead 的路径陷阱

**陷阱 1 — `build.mjs` 会把 `assets/remote/` 一起打进主包，CDN 就白走了。**
`minigame/build.mjs` 的 `copyAssets()`（L35–43）把**整个** `assets/` 目录复制到 `dist/assets/` 与 `wx-dist/assets/`。若 8 帧图放在 `assets/remote/worldtour/` 下，`node build.mjs wx` 会**原样复制进 `wx-dist/`**——走 CDN 的意义归零，而且**不会有任何报错**。
**需要**：`copyAssets()` 增加对 `assets/remote/` 的排除（wx 目标必排除；web 目标可保留以便本地预览）。

**陷阱 2 — 微信小游戏加载远程图片需要域名白名单，开发者工具不校验。**
`platform/wechat.ts: loadImage()`（L212）用 `wx.createImage()` + `img.src`。传 https URL 在**开发者工具里正常**，但**真机**要求该域名已配置在小程序后台的 **downloadFile 合法域名**列表中，否则加载失败。
按现有契约（`app.ts preloadImages` 的 `.catch()` 静默降级），失败**不报错、只是永远没有图**——会静默退化成「8 帧全走 §A.3.1 兜底渐变」。功能不崩，但礼物变成了 8 张纯色渐变。
**需要**：上线前确认 CDN 域名已进白名单，并在灰度阶段真机验证一次。

> **补充说明包体现状**：`minigame/assets/` 当前已达 **67 MB**（43 个文件），远超微信主包 4 MB 上限。这 8 帧走 CDN 是**正确且必要**的决定——但也意味着「CDN 加载」这条能力是**本项目第一次真正用上**（`seedream-pipeline §7.1` 明确记录：现行 Canvas 2D 运行时无 `cc.assetManager`，暂不分包）。**它是新建能力，不是复用能力**，排期上请按新功能对待。

## D.2 调参口径（真机走查时用）

1. **先定两个极端**：第 3 帧（0.14）与第 7 帧（0.09）。这两帧调对了，中间六帧跟随微调即可。
2. **判据不是「好看」，是「同区三帧横排看不出色温断层」**：把 1/2/3 排一起、4/5 排一起、6/7/8 排一起，各组内应读作同一时段的光。
3. **跨组切换判据**：8 帧连续过一遍，不应有任何一帧「跳出来」。若某帧跳出，**先调它自己的 α，不要动整组**。
4. **单帧 α 调整上限 ±0.03**。超过这个幅度说明问题在图本身（色板越界），应打回重出图，不是靠叠层硬压——`scene-backgrounds-spec §3.4` 同款纪律：「不要靠加暗角硬压（会显脏）」。

## D.3 三条实现纪律（给 engineering-lead）

1. **L2 必须在 L3 之前绘制。** `world-tour-reward §2.1` 的 z 序已定（L2 → L3），本文重申**原因**：L2 的 source-over 染色会**抬黑场**（把暗部整体提亮），必须由 L3 的暗角与底部压暗把它压回去。顺序反了，字幕区就会发灰，且 §E 的亮度门全部失效。
2. **合成模式用默认 `source-over`。** 不要用 `multiply` / `overlay` / `soft-light`——微信小游戏 Canvas 2D 对这些 `globalCompositeOperation` 的支持在低端机上不一致，一旦某台机器不支持会**静默回退成 source-over 或直接画错**。`source-over` + α 是唯一全平台可预期的做法。
   > *（可选 P2，需程基岩验证后再议：若真机确认支持 `multiply`，α 提到 0.18 能得到更厚的电影感调色。但这是锦上添花，**不要为它冒兼容性风险**。）*
3. **L2 是全屏矩形 fill，不是图片的一部分。** 它盖在 L1 名胜图之上、**推镜变换之外**——即 L1 在 `save/translate/scale/restore` 里推镜，L2 在 `restore()` **之后**画全屏。若 L2 跟着推镜一起缩放，边缘会露出未染色的一圈。
